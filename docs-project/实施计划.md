# 汽车销量跟踪工具 — 实施计划 v2

> v1 备份见 `实施计划_v1_备份.md`
> v2 核心变化：自动化从收尾工作提升为架构主干；P0 验证环境改为 GitHub Actions

---

## 一、设计目标（v2 新增，统领全文）

**常规月份零人工操作。**

不是"自动抓取 + 人工检查"，而是：系统自己跑、自己校验、
自己判断该不该找人，只有真的需要业务判断时才主动推送到飞书问你。

衡量标准：一个正常的月份，你什么都不用做，
飞书群里会自动出现一条"本月数据已更新"的卡片，点进去就是最新看板。

## 二、已锁定的决策

| 项目 | 决策 |
|---|---|
| 数据来源 | 从公开网站抓取（候选：懂车帝 / 乘联会 / 中汽协） |
| 数据范围 | 近 3 年（2024–2026）· 仅乘用车 · 含能源类型拆分 |
| 图表口径 | 年份单选 → 横轴 1–12 月，纵轴 YTD 累计销量，每个品牌/车型一条折线 |
| 统计粒度 | 可切换：① 厂商品牌 ② 车体类型 → 车型 |
| 最新动态 | 预抓取新闻缓存（非实时联网） |
| 运行环境 | **GitHub Actions**（唯一有完整网络的执行环境） |
| 页面托管 | GitHub Pages（public 仓库，Actions 完全免费） |
| 通知触达 | **飞书群自定义机器人 webhook**（无需管理员权限） |

## 三、硬约束（已实测确认）

**1. 云端容器与本机沙箱均无法访问国内汽车网站**
两条独立验证线均在 TLS CONNECT 阶段被出网网关拒绝：
```
x-deny-reason: host_not_allowed
Host not in allowlist: www.caam.org.cn
```
懂车帝、乘联会、中汽协全部被拒。这是通用出网白名单机制，非站点反爬。
→ **抓取必须跑在 GitHub Actions 上。这一点是定局。**

**2. GitHub 可达**
`api.github.com` 返回 200。
→ 仓库建好后可直接读取 Actions 运行结果，无需人工转述日志。

**3. 无飞书管理员权限**
→ 放弃工作台应用入口，改用群机器人推送 + 群置顶链接。
→ 此路线反而更优：推送式触达 > 拉取式访问。

## 四、自动化工作流（本文档核心）

### 触发时机设计

国内月度销量数据通常在**次月 8–14 日**陆续发布，具体日期不固定。
因此不能只在固定某一天跑。

```yaml
schedule:
  - cron: '0 4 8,10,12,14,16 * *'   # 次月 8/10/12/14/16 日 北京时间 12:00
```

配合**幂等跳过**：每次运行先检查目标月份数据是否已存在，
已存在则直接退出。所以多次触发不会重复抓取，
只会在数据真正发布的那一天成功抓到一次。

### 完整流水线

```
  次月 8/10/12/14/16 日 自动触发
              │
              ▼
  ① 幂等检查 ── 本月数据已存在？ ──是──▶ 退出（不通知，静默）
              │否
              ▼
  ② 抓取销量  失败自动重试 3 次（间隔 5s / 30s / 120s）
              │
        ┌─────┴─────┐
       成功        连续失败
        │             │
        │             ▼
        │      ⚠️ 保留上月数据不覆盖
        │         页面标注「数据截至 X 月」
        │         飞书推送告警 + 日志链接
        │             │
        ▼             └──▶ 结束
  ③ 数据质量守门（任一不通过则拒绝提交并告警）
     · 行数较上月波动 > 30%
     · 上月 Top 20 品牌本月凭空消失
     · 销量出现负数或数量级异常
     · 关键字段大面积为空
              │通过
              ▼
  ④ 未知车型处理（不丢弃、不瞎猜）
     · 规则预归类：名称含 EV/纯电 → 纯电
                   含 DM-i/PHEV/插混 → 插混
                   含 增程/EREV → 增程
                   其余 → 燃油
     · 规则拿不准的 → 写入 unmapped.json，进待确认清单
              │
              ▼
  ⑤ 抓取新闻缓存（各品牌/车型近期动态）
              │
              ▼
  ⑥ 构建 index.html（ECharts + 数据全部内联）
              │
              ▼
  ⑦ git commit + push → GitHub Pages 自动发布
              │
              ▼
  ⑧ 飞书机器人推送卡片
     ┌────────────────────────────────┐
     │ ✅ 2026年8月销量数据已更新       │
     │ 乘用车总销量 XXX 万辆（同比 +X%）│
     │ Top3：比亚迪 / 吉利 / 长安       │
     │ ─────────────────────────────  │
     │ ⚠️ 3 个新车型待确认归类：        │
     │    XXX、YYY、ZZZ                │
     │ ─────────────────────────────  │
     │ [ 打开看板 ]                    │
     └────────────────────────────────┘
```

### 人工介入点（设计目标是趋近于零）

| 场景 | 频率 | 你要做什么 |
|---|---|---|
| 正常月份 | 每月 | **什么都不用做** |
| 新车型待确认归类 | 偶尔 | 飞书里回一句归类结果 |
| 抓取彻底失效（网站改版） | 罕见 | 告诉我，我修脚本 |

关键设计原则：**系统主动找人，人不需要主动检查。**
所有异常都通过飞书推送，你不需要记得去看 Actions 日志或打开看板核对。

## 五、架构

```
GitHub 仓库（public）
├── .github/workflows/
│   ├── monthly.yml          ← 每月自动抓取 + 发布 + 通知
│   └── probe.yml            ← P0 探针（手动触发，一次性）
├── scripts/
│   ├── probe_sources.py     ← 数据源可行性探测
│   ├── scrape_sales.py      ← 销量抓取（Playwright）
│   ├── scrape_news.py       ← 新闻抓取
│   ├── validate.py          ← 数据质量守门
│   ├── build.py             ← 构建 HTML
│   └── notify_feishu.py     ← 飞书卡片推送
├── data/
│   ├── sales.csv            ← 销量长表（唯一数据源）
│   ├── mapping.json         ← 口径映射字典
│   ├── unmapped.json        ← 待确认车型清单
│   └── news.json            ← 新闻缓存
└── docs/index.html          ← GitHub Pages 发布目录
```

**设计要点**

- 单一数据源：所有图表都是 `sales.csv` 的不同 group-by，
  年份筛选、粒度切换、能源筛选全在前端聚合
- 展示层零依赖：ECharts 与数据全部内联在单个 HTML 里，
  无后端、无外部请求，既可在线访问也可下载离线打开
- 层间只通过文件通信：抓取坏了不影响图表，只是数据停在上月

### sales.csv 字段

| 字段 | 说明 |
|---|---|
| year / month | 年份 / 月份 |
| group | 厂商集团（如 一汽大众） |
| brand | 品牌（如 大众） |
| body_type | 车体类型：轿车 / SUV / MPV |
| model | 车型（如 朗逸） |
| energy_type | 能源类型：燃油 / 纯电 / 插混 / 增程 |
| sales | 当月销量 |

## 六、分阶段计划

### P0 · GitHub Actions 连通性与数据源探针 ★ 当前阶段

**为什么在 GitHub Actions 上验证：** 那就是生产环境。
在别处（本地浏览器、云端容器）验证出来的结论，
换到 GitHub 的海外服务器上未必成立 —— IP 地域、Cookie、反爬策略全都不同。

**验证内容**
1. GitHub runner 能否访问懂车帝 / 乘联会 / 中汽协（**最大未知数**）
2. 若可达，逆向出数据接口的 URL、参数、响应结构
3. 六个维度是否齐全（重点：车体类型、能源类型）
4. 历史数据能回溯到哪个月

**你要做的动作**：建仓库 → 上传文件 → 点一次 Run → 告诉我。之后我自己读结果。

**风险预案**：若 GitHub 海外 IP 被目标站点地域限制，
备选顺序为 ① 换用海外可访问的数据源 ② 你本地 Chrome 抓取 + 半自动上传。

---

### P1 · 数据管道 + 质量守门

- `scrape_sales.py`：幂等、可重跑、失败可见
- `mapping.json`：口径映射字典（需你拍板，见第八节）
- `validate.py`：四条质量规则，不通过即拒绝提交
- 回补 2024-01 至今的历史数据

**验收**：同一月份重复运行结果一致；故意喂入脏数据能被守门拦下

---

### P2 · 图表

- 顶部：年份单选 · 粒度切换 · 能源类型筛选
- 车型粒度下二级筛选：轿车 / SUV / MPV
- 主图：X 轴 1–12 月，Y 轴 YTD 累计销量，每系列一条折线
- Top 10 + 「其他」聚合，附搜索勾选补充
- **独立折线 / 堆积面积切换**（独立看增速，堆积看份额）
- 数据不完整时页面顶部标注「数据截至 X 月」

**验收**：切换年份和粒度图表正确重绘

---

### P3 · 新闻缓存与详情抽屉

点击折线或图例 → 右侧滑出抽屉
- 上半：该品牌/车型月度明细、同比、排名变化
- 下半：新闻卡片列表，可点外链

---

### P4 · 全自动化闭环

- `monthly.yml`：定时触发 + 幂等 + 重试 + 降级
- `notify_feishu.py`：成功卡片 / 告警卡片
- GitHub Pages 开启，飞书群机器人配置

**验收**：手动触发一次能完整跑通「抓取 → 校验 → 构建 → 发布 → 飞书收到卡片」

## 七、风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **GitHub 海外 IP 被目标站点限制** | 整个自动化方案不成立 | P0 首要验证项；预案见 P0 |
| **口径不统一**（一汽大众 vs 大众） | 图表碎片化 | `mapping.json` 人工拍板 + 未知项进待确认清单 |
| **新车型持续出现** | 数据缺失或归类错误 | 规则预归类 + 拿不准的推送飞书询问，绝不静默丢弃 |
| **抓到了但数据是错的** | 比抓失败更危险 | `validate.py` 四条守门规则，宁可不更新也不写错 |
| **网站改版导致抓取失效** | 数据停更 | 保留上月数据 + 页面标注截止月份 + 飞书告警 |
| **仓库 60 天无活动导致定时任务被禁用** | 自动化静默停摆 | 每月数据提交天然产生活动；额外加 keepalive 步骤兜底 |
| **GitHub Actions cron 不准时** | 延迟数十分钟至数小时 | 每月跑一次的场景无影响，可忽略 |
| **GitHub Pages 国内访问不稳定** | 同事打不开 | 备选迁至阿里云 OSS / 腾讯云 COS |
| **系列数量爆炸**（品牌 100+、车型 1000+） | 图表不可读 | Top 10 + 「其他」+ 搜索勾选 |

## 八、待拍板的口径决策

以下需要业务判断，技术侧不能代定。建议 P1 开始前确认，改动成本最低。

1. **厂商 vs 品牌**：「一汽大众」与「上汽大众」分开统计，还是合并为「大众」？
2. **车型合并**：「宋PLUS DM-i」与「宋PLUS EV」算一个车型还是两个？
3. **Top N 的 N**：默认显示前 10，还是前 15 / 20？
4. **能源类型分类**：增程（如理想）单独一类，还是归入插混？
