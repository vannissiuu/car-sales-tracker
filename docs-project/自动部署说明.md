# 自动部署说明（2026-09 建立）

## 一、以前是怎么做的，为什么要改

改动流程原本是：Claude 在云端改代码 → 生成 190KB 的 `build.yml` → **人工**在 GitHub 网页上
打开该文件、全选、粘贴、commit → 再手动点 Run workflow。

每改一次就要重复一遍，慢且容易出错（粘贴不全、粘漏文件、忘了点 Run workflow）。

根因是这个项目当初的设计取舍：为了让非技术用户"只粘一个文件就能部署"，Python 源码是以
heredoc **内嵌**在 workflow YAML 里的。这个设计优化了第一次部署，代价是之后每一次更新。

## 二、现在是怎么做的

Claude 在**用户本机的 Cowork 沙箱**里直接 clone / commit / push。

网络与环境事实（2026-09-07 实测）：

| 项目 | 状态 |
|---|---|
| 沙箱内 git | ✅ 2.34.1，架构 aarch64 |
| 沙箱 → github.com（HTTPS） | ✅ 通（走 HTTP 代理） |
| 沙箱 → github.com（SSH 22 / 443） | ❌ DNS 不解析，只放行 HTTPS |
| 沙箱 → pypi / npm / GitHub Releases | ✅ 通 |

因为 SSH 不通，走 **HTTPS + token**；因为挂载进来的 macOS 目录**不允许删除文件**
（git 需要建立和删除 `.lock` 文件），工作副本**不能**放在挂载目录里，只能放在沙箱
`$HOME/work/repo`（随会话销毁，但 clone 只要 2 秒，随时可重建）。

### 凭据

- 通过 **GitHub 官方设备授权流程（Device Flow）** 取得，scope = `repo,workflow`。
  `workflow` 是必须的，否则 `.github/workflows/` 下的文件推不上去。
- 授权时验证码显示在对话里，token 由 GitHub 直接下发到沙箱落盘，**从未经过对话**。
- 存放位置：`汽车销量/.deploy/git-credentials`（权限 600）。
- **撤销方式**：GitHub → Settings → Applications → Authorized OAuth Apps → GitHub CLI → Revoke。
  撤销后重新走一次设备授权即可，不影响仓库里的任何东西。
- 这是一个能推送本仓库的凭据。不要把 `汽车销量` 文件夹整个转发给别人；如果该目录开了
  iCloud 同步，它会被同步到云端。

### 每次会话的引导

```bash
bash ~/.../汽车销量/.deploy/bootstrap.sh
```

重建 `$HOME/work/repo`（浅克隆，depth 20），并写好 credential helper 和提交身份。约 2 秒。

**注意**：每次 push 之后，Actions 会紧接着往仓库推一个 `chore: build dashboard [skip ci]`
提交，本地副本立刻就落后了。所以**下一次提交之前一定要先 `git pull --rebase`**，
否则 push 会被 non-fast-forward 拒绝。

### 一次改动的完整链路

```
用户提出修改
      ↓
Claude 在云端容器改 src/build.py，重新生成 build.yml，
跑 tests/verify_scope_filter.py（100 条）+ verify_capmonth12_edge.py（7 条）
      ↓  全绿才继续
把改动落到本机 $HOME/work/repo
      ↓
git commit + push
      ↓
GitHub Actions 自动重建 docs/index.html → GitHub Pages 自动发布
```

用户需要做的操作：**零**。

## 三、Claude 给自己立的规矩

1. **回归测试不全绿，不 push。** 测的是构建产物 `docs/index.html`，不是源码；跑之前必须
   确认产物是刚重建的那一份。
2. **凡是会改变线上看板的 push（碰 `.github/workflows/`、`src/`、`data/`），推之前先把
   "改了哪些文件、提交信息是什么"念给用户，用户说走才走。** 纯文档改动（`docs-project/`、
   `README.md`）不触发构建，推完再报备即可。
3. **只推 `car-sales-tracker` 这一个仓库。** 不碰用户机器上的其它任何目录。
4. **绝不把任何凭据写进仓库。** token 只存在 `.deploy/git-credentials`，该目录不在仓库里。
5. **`src/` 与 workflow 内嵌副本必须保持一致。** 改完 `src/build.py` 后用 `tools/` 下的
   生成器重新生成 YAML，并校验：YAML 可解析、内嵌 Python 可编译、提取回来与源文件逐字节
   一致（允许结尾换行差异）、`workflow_run.workflows` 名称未被改动。

## 四、坏掉了怎么办

- **push 报 403 / 认证失败** → 授权被撤销或过期，重新走一次设备授权即可。
- **沙箱连不上 github.com** → 网络策略变了，退回人工粘贴流程（见 README「修改代码的正确姿势」）。
- **本机沙箱不可用（电脑没开、没链接）** → 同上，退回人工流程。
- **git 在挂载目录里报 `Operation not permitted`** → 工作副本被误放进了挂载目录，
  按第二节说明放回 `$HOME/work/repo`。

## 五、内嵌 heredoc 已拆除（2026-09-07 完成）

原先 `src/*.py` 是用 heredoc **内嵌**在 workflow YAML 里的，workflow 运行时先把源码写出来
再执行。这个设计优化了"第一次部署只需粘贴一个文件"，代价是 YAML 巨大、缩进敏感、diff 不可读。
人工粘贴退出主链路之后这个取舍不再成立，已拆除：

| 文件 | 改造前 | 改造后 |
|---|---:|---:|
| `.github/workflows/build.yml` | 3,521 行 | 96 行 |
| `.github/workflows/probe.yml` | 2,559 行 | 159 行 |
| `.github/workflows/probe_news.yml` | 598 行 | 75 行 |
| `.github/workflows/archive.yml` | 899 行 | 已删除 |

`archive.yml` 是当初一次性把 `tests/` `tools/` `docs-project/` 和 README 塞进仓库的工具
（内容是 749 行 base64 包裹），任务早已完成，留着只会让人误点 Run，随本次改造一并删除。
需要时从 git 历史里取回。

改造内容：删掉三个 `Write xxx script` 步骤；`probe_news.py` 从仓库根提升为
`src/probe_news.py`（它用 `os.getcwd()` 定位输出目录，位置变化不影响
`probe_news_output/` 的落点）；commit 步骤的 `git add` 去掉 `src/`（运行期不再改写它）。

改造前做的验证：

1. **产物等价**：仓库里的 `src/build.py` 直接运行，产出的 `docs/index.html`
   与线上那份**字节数完全相同（1,412,815）**，全文唯一差异是两处构建时间戳。
2. **内嵌副本与 `src/` 一致**：`sync_script.py`、`notify_feishu.py`、`probe_news.py`
   从 YAML 提取出来与仓库里的文件逐字节一致（仅结尾换行差异），所以删掉 Write 步骤
   在行为上是空操作。
3. **结构 diff 干净**：把旧 YAML 的 heredoc 整块折叠后与新 YAML 逐行 diff，
   除了该删的三个步骤、三条新增注释、两处 `git add`，没有任何其它改动。
   触发器、`if:` 条件、`continue-on-error` 计数、`id: run_sync`、
   `SYNC_NOTEWORTHY` 等关键字段逐个核对过。

`tools/` 下的生成器随之退出流程，保留备查。

## 六、顺带修掉的一个旧 bug：链式触发时看板从来没被自动发布

拆 heredoc 之后做端到端实测，发现了一个**一直存在、一直被吞掉**的问题：

| 触发方式 | 构建 | 提交发布 |
|---|---|---|
| 数据同步完成后链式触发（`workflow_run`） | 跑了 | **没推上去** |
| 在 Actions 里手动点 Run workflow（`workflow_dispatch`） | 跑了 | 推上去了 |

原因：`build.yml` 的 checkout 步骤写的是
`ref: ${{ github.event.workflow_run.head_sha || github.ref }}`。链式触发时它 checkout 的是
一个**具体的 commit SHA**，git 处于 detached HEAD 状态，后面不带参数的 `git push` 必然报
"You are not currently on a branch"。重试逻辑里用的 `git pull --rebase` 在 detached HEAD 下
同样没有上游可跟。三次失败后只打印一条警告，步骤仍然退出 0——`continue-on-error: true`
把整件事吞成了"成功"。

后果：每月 25 日数据同步完之后，自动构建"显示成功"，但看板从来没被更新，必须有人
手动去 Actions 里点一次 Build。这解释了为什么手动点 Run workflow 一直在日常流程里。

修法（2026-09-07）：

- 显式 `git push origin HEAD:"$BRANCH"`，detached 与否都成立；
  `$BRANCH` 取自 `github.event.workflow_run.head_branch || github.ref_name`。
- 重试改成 `git fetch origin "$BRANCH"` + `git rebase FETCH_HEAD`
  （用 FETCH_HEAD 是因为 actions/checkout 是浅克隆 + 定制 refspec，
  远端跟踪引用 `origin/$BRANCH` 不一定被更新）。
- 三次都失败时 `exit 1`。步骤仍是 `continue-on-error`（不拖垮整个 job），
  但在 Actions 界面上会显示成失败，不再是一片绿。

**教训**：`continue-on-error: true` 让失败不阻塞流程，但也让失败不可见。凡是加了它的步骤，
内部必须自己判断成败并显式 `exit 1`，否则就是在给自己造一个永远不会响的警报。
